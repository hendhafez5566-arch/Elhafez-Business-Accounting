# إرسال المتابعة بهوية محفوظة — 2026-10-15

## السلوك المنفّذ

زر جدولة المتابعة في الشاشة الأصلية لم يعد يرسل طلبًا بلا هوية. يتحقق من
الجلسة والبيانات وعبارة الحماية، ثم يحفظ نسخة مشفرة من بيانات الإرسال وهوية
عشوائية ثابتة داخل IndexedDB قبل أي POST، وينتظر اكتمال معاملة التخزين.
يرسل بعد ذلك عبر crmRequest والسياق الموثق للشركة والفرع وقت بدء العملية.
مهلة HTTP عشرون ثانية؛ فشل الاتصال أو الرد لا يحذف الطلب.

يمكن استرجاع الطلب المحفوظ وإعادة إرساله يدويًا. الإعادة تستخدم النسخة
الأصلية وهوية requestId نفسها، حتى بعد إعادة تشغيل المتصفح، ولا تستخدم أي
تعديلات لاحقة في النموذج. لا إعادة تلقائية عند عودة الشبكة. تغيير الحساب أو
الفرع أثناء التشفير يمنع إرسال العملية تحت الجلسة البديلة.

طلب الإرسال منفصل عن المسودة العادية، لذلك حذف أو استبدال المسودة لا يحذفه.
لا ينسخ طلب جديد فوق طلب مجهول النتيجة. قيد مقارنة وكتابة ذري داخل IndexedDB
يجعل تبويبين يتفقان على نفس الطلب المحفوظ بدل توليد طلبين مستقلين. عند قبول
الخادم يُحفظ رقم المتابعة وحالتها محليًا؛ الرد الناقص لا يعتبر تأكيدًا. إن
فشل تثبيت التأكيد محليًا يبقى الطلب قابلًا للإعادة بنفس هويته.

زر «بدء متابعة جديدة بعد التأكيد» يحرر خانة الإرسال بعد قراءة تأكيد محفوظ
وفقط إذا كانت نفس الهوية لا تزال موجودة. لا يحذف طلبًا معلّقًا. يبقي العميل
والمسؤول ونوع التواصل، ويفرغ الموعد والإجراء التالي. طلب واحد لكل مستخدم وفرع
وشركة في المتصفح الحالي؛ ليس قائمة إرسال متعددة العناصر.

## التحقق المنفّذ

اختبار المتصفح يجمع مكونات الإنتاج نفسها ويستخدم HTTP فعليًا إلى سيرفر fixture
محلي بذاكرة قبول؛ ليس بديلًا عن قبول Nest/JWT/PostgreSQL كمسار كامل. نجحت
13 حالة (14 مع الاختبار الأب):

1. لا إرسال بدون عبارة حماية صالحة.
2. الحفظ المشفر أثناء انقطاع الإنترنت قبل الاتصال.
3. حذف المسودة لا يحذف طلب الإرسال.
4. غلق عملية المتصفح وفتح نفس ملفه الشخصي يحتفظ بنفس الهوية؛ قطع الرد جزئيًا
   بعد قبول fixture يترك النتيجة قابلة للإعادة.
5. رفض حذف المجهول أو استبداله بتعديل نموذج جديد.
6. الإعادة ترسل البيانات الأصلية وتثبت التأكيد؛ المؤكد لا يرسل مرة أخرى.
7. فشل الكتابة المحلية يمنع POST.
8. تبويبان يتفقان على هوية واحدة.
9. رد نجاح ناقص يبقي الطلب قابلًا للاسترجاع بنفس الهوية.
10. رفض التفويض لا يحذف الطلب، ويمكن إعادة نفس الطلب بعد تغير السماح.
11. عبارة خاطئة أو مستخدم آخر لا يعيدان إرسال الطلب الأصلي.
12. تغيير المستخدم أثناء التشفير يمنع الإرسال بحساب بديل.
13. انتهاء مهلة HTTP يحافظ على الهوية حتى لو كان الخادم قد قبل الطلب.

## الحدود القائمة

هذا يربط الإرسال اليدوي بالهوية، ولا يجعل النظام كله أوفلاين. إعادة تشغيل
المتصفح في الاختبار تحمل الشاشة أونلاين أولًا. الجهاز يحتاج HTTPS أو سياقًا
محليًا موثوقًا لتوفير Web Crypto. المسودة وطلب الإرسال ليسا نسخة احتياطية،
وفقد عبارة الحماية أو حذف بيانات المتصفح يفقد الوصول إليهما.

رفض نهائي يحتاج مسار مراجعة وتسوية لاحقًا؛ لا نوفر حذفًا تلقائيًا لطلب مجهول
أو ادعاء قبول مرفوض. خطأ تحقق domain من API لا يفترض أن له حالة HTTP بعينها
في اختبار العميل هذا. التغيير لا يعدل معالج أخطاء Nest ولا يثبت JWT/RBAC
الحقيقي أو قاعدة البيانات في نفس اختبار المتصفح. الاختبار الأصلي للقاعدة
يستخدم fixtures للتفويض والعميل المحتمل. التدقيق العام يظل خارج معاملة الجدولة
كما هو موثق سابقًا. لا مزامنة مالية أو إرسال واتساب أو نشر ضمن هذا التغيير.
