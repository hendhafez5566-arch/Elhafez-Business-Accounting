# اتفاق تقسيم عمولة المندوب الرئيسي والتابع

## ما أُضيف

اتفاق تجاري ذو نسخ محفوظة، يحدد نسبة الرئيسي من العمولة المتفق عليها ونسبة التابع المكملة إلى ١٠٠٪. يدعم أن تكون العمولة كلها لأحدهما أو موزعة، حتى ست خانات عشرية بحساب BigInt دقيق؛ ليست النسب من سعر البرنامج. لا يشمل التوزيع مبالغ ثابتة أو عدة مستفيدين أو الموظف في هذه الخطوة.

الحفظ في جدول am_commission_agreements المملوك لوحدة agent-management، بعلاقة مركبة بالشركة إلى المندوبين. البيانات تتضمن رقم النسخة، النسب، مرجع/سبب الاتفاق، الفاعل والتاريخ وهوية طلب ثابتة. لا توجد عملية تعديل أو حذف لنسخة؛ التغيير بإضافة نسخة جديدة. المهاجرة الجديدة فقط تضيف الجدول وفهارسه وشروط النسب والنسخة والطرفين.

API:

- GET /crm/agents/:id/commission-agreements: قراءة الرئيسي وقت التحميل وقائمة النسخ، بصلاحية القراءة.
- POST للمسار نفسه: حفظ نسخة بصلاحية إدارة المندوبين، مع requestId وparentAgentId وexpectedVersion وprincipalPercent وreason.

إعادة نفس الطلب بنفس البيانات والفاعل تعيد نفس النسخة. تغيير البيانات تحت نفس الهوية يُرفض. حفظان متنافسان لنفس النسخة السابقة لا يكتبان فوق بعضهما. يستخدم الحفظ نفس قفل الشركة الخاص بتغيير علاقة الرئيسي، حتى لا يعتمد اختيارًا قديماً للرئيسي. الفاعل والشركة من السياق الموثوق ولا يؤخذان من جسم الطلب.

تغيير الرئيسي لا يمحو الاتفاق القديم ولا يجعله اتفاقًا مع الرئيسي الجديد. تبقى النسخ مراجع تاريخية. تدقيق platform-core المعتاد خارج معاملة الاتفاق مثل عمليات المندوب الحالية؛ قد ينتج عن إعادة المحاولة سجل تدقيق إضافي، لكن لا نسخة اتفاق إضافية.

## الواجهة

قسم المندوبين يحتوي اختيار التابع، والرئيسي عند آخر تحميل، ونسبة الرئيسي ومرجع الاتفاق وجدول النسخ القديمة. الحفظ يدوي ويحتاج الخادم. بعد نتيجة غير مؤكدة تُقفل بيانات الطلب وتستخدم إعادة المحاولة نفس الهوية والبيانات. التحديث والمراجعة يجلبان حالة الخادم قبل إدخال نسخة مختلفة. طلب الحفظ له مهلة ٢٠ ثانية، والقراءة ١٥ ثانية؛ انتهاء المهلة لا يعني أن الحفظ لم يحدث.

## الأدلة

نجحت ٦ حالات وحدة جديدة، مع ١١ حالة المندوبين السابقة (١٧ إجمالًا): دقة النسب وحدودها، إعادة المحاولة، النسخ والتعارض، تغير الرئيسي وحفظ التاريخ، السباق وحفظ الشروط الأصلية، وعزل الشركة والتعليق.

نجحت ٣ حالات Chromium جديدة (٤ مع الأب) على المكون الحقيقي وHTTP fixture: القراءة بلا كتابة، قطع الرد بعد تسجيل الاتفاق ثم الإعادة بهوية واحدة، حفظ نسخة جديدة مع بقاء القديمة ورفض غير المخول. ونجحت حالات واجهة العلاقات الخمس السابقة. هذا fixture لا يثبت API الحقيقي أو القاعدة.

أضيفت ٣ حالات PostgreSQL لقبول طلبات متزامنة بإيصالات ثابتة وتنافس نسخ جديدة، حفظ التاريخ بعد تغيير الرئيسي، وقيود مجموع النسب داخل القاعدة. وأضيفت حالة HTTP حقيقية للتحقق من الدقة والهوية وسياق الفاعل، وتوسعت حالة الصلاحيات لتشمل الاتفاقات. تُشغّل في بيئة CI المؤقتة القائمة؛ النتيجة الحالية في PR #146. لم تُشغّل قاعدة PostgreSQL محليًا هنا.

## ما لم يُنجز بعد

هذا اتفاق تجاري وليس مطالبة عمولة أو قيدًا أو سدادًا أو موافقة مالية. لم يُربط تلقائيًا بحجز أو خدمة، ولا يغير مطالبة أو حجزًا سابقًا. تطبيقه ماليًا يحتاج حفظ نسخة الاتفاق مع الحجز وتوزيع الاستحقاقات عبر مالكها expense-commission-recognition ومنسقها الحالي، مع الإلغاء والتسوية والاستئناف. لا دمج لأرصدة الطرفين ولا معالجة للتقريب النقدي متعدد العملات هنا. G04 باقٍ جزئيًا؛ لا إعلان اكتمال العمولات أو النظام.
