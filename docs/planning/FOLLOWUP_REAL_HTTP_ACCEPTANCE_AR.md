## ما أصبح موثقًا بالتنفيذ

شغّل الاختبار AppModule الإنتاجي بكامل وحداته وAPP_GUARD الحقيقي، مع نفس
GlobalRequestSafetyPipe وPlatformErrorFilter. استخدم جلسات Bearer الفعلية
المخزنة على الخادم، وتحقق TOTP الفعلي لمالك المنصة، وبيانات في PostgreSQL.
لم يستبدل خدمة صلاحيات أو اشتراك أو عميل محتمل بمزود وهمي.

أنشئت بيانات الشركات والمستخدمين والاشتراكات على قاعدة الاختبار المؤقتة فقط.
التهيئة تتم عبر HTTP لمالك المنصة، ثم دخول الشركة وتغيير كلمة المرور الأولية
وإنشاء العميل المحتمل عبر HTTP. إعداد دور الموظف المحدود وتعديل صلاحياته
والوصول للفرع يستخدمان خدمة Platform Core العامة، وليس كتابة مباشرة لجداولها.
مفاتيح التهيئة وMFA وكلمات المرور عشوائية ومؤقتة ولا تحفظ في المستودع.

نجحت **10 سيناريوهات** (11 اختبار Node مع الأب):

1. تهيئة مالك فعلي، وتسجيل دخول بـMFA، وإنشاء شركتين وخطط اشتراك لها CRM.
2. منع العمل بكلمة مرور مؤقتة، ثم السماح بعد تغييرها وإنشاء عميل محتمل حقيقي.
3. عشرون POST متزامنًا بنفس الهوية ينتجون متابعة واحدة وحدث SCHEDULED واحدًا.
4. رفض محتوى مختلف بنفس الهوية وبيانات غير صالحة بـ400، دون جدولة إضافية.
5. رفض غياب التوكن وتزوير الشركة أو الفرع.
6. وكيل HTTP يقطع الرد جزئيًا بعد اكتمال رد API الحقيقي وقبول قاعدة البيانات؛
   الإعادة ترجع نفس رقم المتابعة وحدث جدولة واحدًا.
7. موظف غير مدير يعمل بصلاحية فعلية، ثم ترفض إعادة طلبه بعد سحبها، وتنجح
   عند إعادة منحها.
8. سحب وصول الفرع يمنع الإعادة رغم بقاء الجلسة صالحة.
9. إلغاء المتابعة لا ينعكس عند إعادة أمر الجدولة الأصلي.
10. تعليق الاشتراك يمنع الإعادة؛ وبعد استئنافه، تسجيل الخروج يلغي جلسة Bearer
    فعلًا وتُرفض الإعادة بتلك الجلسة.

`{code:'VALIDATION_ERROR',field,message}`. لا يعيد تصنيف خطأ تفويض أو قاعدة
بيانات كخطأ بيانات؛ يتركهما لمعالجهما الأصلي. أضيف تحقق لأنواع الحقول في

nextAction بنوع غير صحيح. لا تغيير في معالج الأخطاء العام أو صلاحيات المستخدم.
